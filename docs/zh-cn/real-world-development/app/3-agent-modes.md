我们先为项目添加了一项小功能，但更复杂的更改需要更完善的流程。GitHub Copilot app 支持组织现有的工作流程，帮助我们用正确的方法构建所需功能。从本课开始，你将通过几节课遵循典型的智能体驱动开发流程：先使用议题生成新功能，确认代码有效且功能行为符合预期，最终将更改成功合并到项目中。

> [!NOTE]
> 后续功能工作流将沿用同一个会话。通常，不同类型的文件会使用不同会话或 PR；这里会采用简化方式，以便专注于核心概念。

本课将：

- 从 GitHub 议题启动新的智能体会话。
- 在 **Plan** 模式中定义需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续完成该功能时，你将更新存储库指令、自定义现有的 `quality-checks` 技能、添加模型上下文协议 (MCP) 验证、创建质量保证 (QA) 智能体并打开功能拉取请求 (PR)。

## 场景

Tailspin Toys 的游戏目录不断扩大，访问者需要按类别和发行商缩小游戏范围。待办事项中的议题描述了该功能，但多个类别如何组合等细节需要在编码前达成共识。你将使用 Plan 模式确定这些决策，然后授权 Autopilot 在明确范围内实现功能。

## 背景

将人工智能 (AI) 编码智能体引入开发流程不会改变基本原则。事实上，这些原则反而更加重要。大多数开发者遵循类似以下的流程：

1. 打开已创建的议题，查看需要完成的工作详情。
2. 为需要构建的内容制定计划。
3. 构建并审查代码。
4. 运行测试以验证代码。
5. 手动验证新功能。
6. 创建拉取请求 (PR)。
7. 代码通过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数流程都与上述步骤相似。

坚持这种标准方法，可以确保 AI 生成的代码满足既定要求，并像手写代码一样经过审查。

## 会话模式

**会话模式**控制智能体的自主程度。可以从提示字段下方的下拉菜单中设置模式，也可以随时更改：

- **Interactive**：你与智能体协同工作。智能体提出更改建议，并等待你的输入后再继续。
- **Plan**：智能体先创建计划。你审查并批准计划后，智能体才会执行。
- **Autopilot**：智能体完全自主工作，包括编写代码、运行测试和迭代，无需等待输入。

先在 Plan 模式中审查计划，再使用 Autopilot 实现。

## 从议题启动会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 已更新。

1. 在侧边栏的 **Sessions** 下选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是预先创建的议题，无需再创建。
2. 选择 **New session**，并选择基于更新后 `main` 创建的 **new working tree**。

   ![GitHub Copilot app 中的议题视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认议题已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让智能体运行 `node --version` 和 `npm --version`。如果命令在终端中能运行，但在会话中无法运行，请检查应用的 PATH 或版本管理器设置，然后完全退出并重新打开应用。重新尝试失败的操作和检查；不要仅因智能体找不到 npm 就重新安装 npm。

## 规划筛选功能

规划可以在 Copilot 编写代码前审查实现方案。由于会话从议题启动，Copilot 已获得功能请求的上下文。发送以下提示：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并对照议题的验收标准审查计划。确认计划涵盖类别和发行商筛选、无障碍控件、数据访问更改和测试。讨论尚不明确的行为，例如多个类别如何组合，以及没有游戏匹配时应如何处理。

计划应使用项目现有工具运行 lint、单元测试、端到端 (E2E) 测试和类型检查。将范围限定为实现和测试筛选功能；完成质量工作流后再创建 PR。批准前，要求 Copilot 修改计划中的问题，并保留议题 URL 和已达成共识的说明，以便后续验证。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中含义相同的选项。不要假定批准计划会自动切换模式；确认当前模式指示器显示 **Autopilot**。

Copilot 随后会开始实现功能，按照既定计划迭代、生成代码并运行测试。

> [!NOTE]
> 批准后可能立即开始实现，因此应先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，应先解决环境设置问题，再认定检查已完成。只停止自己启动的服务器。

## 审查并验证实现

代码生成后，和其他代码一样，合并前需要审查。接下来审查代码并运行网站，确认功能正常。

1. 打开 **Changes**，检查筛选功能实现和测试。
2. 对照议题和已批准的说明检查结果，包括多个类别和发行商组合。确认更改遵循现有存储库指令。
3. 检查 lint、单元测试、端到端测试和类型检查的输出。跳过的检查不能算通过。
4. 接受实现前，解决失败项并重新运行受影响的检查。Playwright 的端到端配置会构建并提供预览服务，而且可能复用本地服务器；确认被测服务器属于此工作树，而不是之前课程的工作树。

## 探索新功能

代码看起来没有问题，但能否正常运行？像之前一样启动应用，并在浏览器画布中打开网站。

1. 使用以下提示，让 Copilot 启动应用并在浏览器画布中打开页面：

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择一个类别，确认显示结果与该类别匹配。清除筛选后，选择一个发行商并确认结果匹配该发行商。
4. 同时设置类别和发行商筛选，并对照议题和已批准的计划检查结果。如果支持多个类别，还要验证已经确定的组合行为。
5. 测试没有匹配游戏的组合，检查空结果状态。清除或重置筛选条件，确认完整列表重新显示。
6. 完成后，使用以下提示让 Copilot 停止为此会话启动的开发服务器并关闭浏览器画布：

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 在后续课程中保留此会话

暂时不要创建或合并筛选功能 PR。练习 4 到练习 8 会继续使用此会话、工作树和分支。接下来将把自定义指令应用于筛选代码，再添加技能和 QA 改进，最后在练习 8 中创建并合并综合 PR。停止开发服务器后，可以让会话保持空闲，并在下一练习中返回同一会话。
